## Preserved production authorities

`ControllerReadinessService` is the production authority for controller/vJoy/HidHide inspection, narrow HidHide mutation, read-back, rollback, recovery journal, reconnect verification, and final DirectInput/report proof. Its existing `applyHidHideConfiguration`, `allowlistMapperOnly`, managed physical-input visibility, and managed virtual-output visibility operations remain the only in-app mutation routes.

`Setup Truth` and the existing Setup Repair Session retain their current state semantics and orchestration. The existing elevated helper contract remains unchanged. `AppIssue` and `AppHealthService` remain the single application-problem model and aggregate.

The mapping hot path remains outside this work: no health observation, process launch, Windows API query, QML event, allocation, logging, or mutex enters DirectInput report handling, `MappingWorker`, vJoy per-report output, Adaptive Response, or profile-control processing.

## Additive V2.6.5 seam

`HidHideHealthService` will be a dedicated control-plane subsystem. It will consume bounded read-only evidence and the current readiness snapshot, derive typed dimensions/findings/action classification, and project the result into QML and canonical `AppIssue` values. It does not replace Controller Readiness, Setup Truth, or the repair helper.

The service will support a lightweight, coalesced essential scan and one asynchronous full scan at a time. Scan results carry a context generation and are discarded when the selected rig/controller/output context changes. A complete scan failure is evidence of incomplete inspection, never proof that HidHide is absent or permission to mutate.
