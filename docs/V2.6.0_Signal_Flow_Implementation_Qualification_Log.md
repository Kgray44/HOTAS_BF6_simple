### Canonical-model audit and decisions

The V2.5.4 canonical configuration is `MapperConfiguration`, persisted by `ConfigStore` and compiled by `MappingWorker` into bounded runtime data. Existing focused editors mutate `AxisMapping`, `ButtonBinding`, `PovBindings`, `AdaptiveResponseLayer`, profiles, and Device Rigs through `AppBackend::persistAndApply()`.

Existing axis and binding arrays cannot faithfully represent all required Signal Flow topology: they lack durable route/processor identity, segment identity, analog fan-out, explicit analog fan-in/Mixer identity, shared processor channel identity, and targetable processor segments. Therefore V2.6.0 must add one centrally persisted canonical Signal Flow topology owned by `MapperConfiguration`, migrate the existing focused-editor mappings into it deterministically, and compile the same topology into bounded runtime structures. Signal Flow will not own a parallel graph-local mapping store.

The graph model will provide canonical endpoint, edge, route, processor-port, processor-channel, and processor-configuration identity. Workspace positions, collapsed groups, pan/zoom, wire style, density, pin/lock state, and inspector width remain separately persisted presentation metadata. This satisfies `SF-ARCH-001` through `SF-ARCH-004`, `SF-MODEL-001` through `SF-MODEL-007`, I-01 through I-05, and I-20 through I-24.

### Durable identity lifecycle

Initial migration will sort canonical source/destination/processor keys and backfill IDs deterministically from a namespaced cryptographic key plus a durable lifecycle generation. Creation allocates a fresh generation; ordinary settings and layout edits preserve identity; undo/redo restores the original identity when it restores that object; deletion records a tombstone generation; recreation receives a new identity; copied/imported profiles are assigned collision-safe identities scoped to their resulting profile/rig identity. No identity derives from visual position or mutable friendly text.

### Transaction and stale-state decisions

Signal Flow commands will carry the canonical revision observed at gesture creation and revalidate at commit. A command will store a revision precondition; any conflicting focused-editor, profile, import, or device change invalidates its routing undo/redo entry instead of overwriting newer canonical state. Layout-only history may remain local because it cannot change routing. A single-input/single-output processor can bypass only after validation; removal of a fan-in processor cannot synthesize an implicit merge and must require a visible replacement decision or remove affected routes atomically.

### HOTPATH baseline and frozen budget

Command used after a clean Release configure with Qt 6.8.3 / MSVC 2022:

```text
C:\\hotas-builds\\v260-signal-flow-phase0\\mapping_hot_path_benchmark.exe
```

The selected primary scenario is the existing worst representative route workload, `idle Adaptive All 8 Axes`. Six independent runs produced:

| Metric | Observed range | Median | Frozen V2.6.0 limit |
|---|---:|---:|---:|
| Typical latency | 1.6–2.0 us | 1.7 us | <= 2.0 us |
| p95 latency | 3.2–3.7 us | 3.4 us | <= 4.0 us |
| p99 latency | 4.0–4.8 us | 4.25 us | <= 5.0 us |
| Throughput | 418,459–499,974 reports/s | 485,036 reports/s | >= 410,000 reports/s |
| Heap allocations/report | 0 in every run | 0 | exactly 0 |

The benchmark’s 0.1-us quantization and run-to-run p99/throughput spread make a nominal three-percent threshold statistically dishonest. The limits above use the smallest defensible whole-tick envelope around the observed measurement range and may not be relaxed after implementation. Signal Flow must add no report-path graph traversal, QML activity, locks, logging, serialization, or allocation (`SF-PERF-001` through `SF-PERF-008`, I-35 through I-39).
