# v2.6.3 — Verified Multi-Controller Profiles & Readiness

v2.6.3 is one of the largest HOTAS BF6 updates in the 2.6.x line. It builds on the Setup Truth & Repair foundation introduced in v2.6.2 and substantially expands the app’s real-world multi-controller workflow, Profile editing model, Device Rig behavior, setup/readiness semantics, Flight Deck UX, live telemetry, and native DirectInput handling.

The primary v2.6.3 release PR changed **70 files** with **12,054 additions and 1,490 deletions**, followed by a small release-fixture correction before the final tag. This is much more than a cosmetic hotfix: it materially changes how controllers, Profiles, Device Rigs, setup state, and editor context interact.

## Highlights

### Multi-controller support is now a first-class workflow

Controller verification, selection, reconnect behavior, optional/required Rig membership, and per-device editing were hardened for setups containing multiple physical controllers.

- **Verify Controller uses exact controller identity.** Verification is tied to the exact saved controller record instead of relying on a single implicit “current controller.”
- **Verification is independent of Rig membership.** A controller can be discovered and verified before it is added to a Device Rig.
- **Required and optional Rig members are treated differently.** Optional devices can be absent or advisory without unnecessarily blocking an otherwise healthy Rig.
- **Reconnect handling is more deliberate.** Controller identity, physical acquisition, inventory refresh, and Rig readiness are treated as separate pieces of evidence rather than one overloaded “verified” flag.
- **Forget Controller performs real cleanup.** Saved controller references are removed instead of leaving stale or ghost device entries behind in Device Rigs.
- **Selected Device is editor context.** Changing which controller is being viewed/edited is not supposed to activate a Rig, rerun global setup, or silently mutate mappings.

This is a major step toward reliable HOTAS + throttle + pedals + gamepad configurations rather than treating the entire app as though only one physical controller can ever exist.

## Profiles: selected, active, blank, copied, and per-device

The Profile workflow received a substantial restructuring.

### Selected Profile vs Active Profile

Profiles can now be viewed and edited independently from the Profile currently driving the mapper.

This allows users to:

- edit one Profile while another remains active;
- browse Profiles without changing runtime behavior;
- activate a selected Profile explicitly;
- clearly distinguish **VIEWING** from **ACTIVE** state.

### Blank Profile creation

Profiles can now be created as genuinely blank configurations instead of requiring an existing Profile to be copied.

A blank Profile does not invent physical axis/button routes. Copying an existing Profile remains available when the user actually wants inherited configuration.

### Category workflow improvements

Profile/category behavior was strengthened with:

- correct category placement during Profile creation;
- safer Profile movement between categories;
- explicit category deletion behavior;
- clearer handling of Profiles contained by a category;
- stronger Profile Library persistence and selection behavior.

### Per-device source mappings

Profile input configuration now distinguishes physical devices explicitly. A mapping belongs to a specific controller/input source instead of assuming every connected controller shares one anonymous axis/button namespace.

That means switching the global Selected Device context can show the selected controller’s own mapping configuration without pretending another controller’s routes belong to it.

## Intentional shared-output mixing

v2.6.3 strengthens explicit collision ownership for cases where more than one physical input targets the same virtual destination.

Intentional shared-output routing can use canonical Mixer behavior instead of treating every duplicate destination as an error. The supported Mixer choices include the established behaviors such as:

- **Sum / Clamp**
- **Larger / Highest-Magnitude value**
- **Average**

The important architectural point is that intentional mixing uses the same canonical Signal Flow/mapping representation rather than creating a second unrelated “settings-page mixer” system.

## Device Rigs and Profiles are more independent

A Device Rig represents hardware topology. A Profile represents control behavior.

v2.6.3 strengthens that separation in runtime behavior.

A healthy Device Rig can become active even when no compatible Profile is currently available. Instead of trapping the user in a circular dependency, the app can enter a safe active/unmapped state and let the user create, choose, or edit a Profile afterward.

This removes the old failure mode where:

1. a Rig could not activate because no Profile referenced it;
2. but the user effectively needed the Rig active in order to build the Profile that would use it.

Rig activation and Profile activation are now treated as separate concerns at the user-facing/runtime level.

## Setup Health and readiness improvements

The v2.6.2 Setup Truth system received another major reliability pass.

### Better setup convergence

Controller verification, inventory refresh, reacquisition, RigStatus, activation state, and final Setup Truth are more deliberately recomputed after setup changes rather than requiring repeated manual checks to discover state that the app itself just changed.

### Required vs optional failures

Setup Health distinguishes actual blockers from advisory conditions.

Examples:

- required controller unavailable → blocking;
- optional controller unavailable/unverified → advisory where safe;
- transient inspection delay → informational when trustworthy last-known-good evidence remains available.

### HidHide timeout handling

A transient HidHide inspection timeout is not treated as proof that HidHide is misconfigured. Controller identity and HidHide isolation/read-back are separate facts, and previously verified healthy evidence can remain usable when a fresh control-plane probe is temporarily delayed by system load.

### Rig-scoped vJoy repair

vJoy inspection/repair is scoped to the selected/setup-target Rig and its actual primary Virtual Output instead of silently relying on unrelated global or Profile-owned output assumptions.

## vJoy and Virtual Output improvements

Virtual Output workflows were expanded substantially.

### Canonical Create Virtual Output experience

v2.6.3 adds a shared `CreateVirtualOutputDialog` so Virtual Output creation no longer needs multiple inconsistent mini-dialogs depending on where the user starts.

The canonical flow supports the established creation styles such as:

- matching an existing output contract;
- using a preset;
- creating a custom output with explicit capability choices.

### Better output state semantics

The app now has stronger distinctions between concepts such as:

- configured descriptor;
- available output;
- acquired/owned output;
- busy output;
- runtime write/report health.

This avoids collapsing every vJoy problem into one vague “unavailable” state.

## Flight Deck UX improvements

Flight Deck received a broad workflow and presentation pass.

### Global Selected Device context

The top-bar Selected Device control is used as the editor context for device-specific surfaces. Device selection is intended to change which physical controller’s settings and telemetry are being inspected, not silently change runtime topology.

### Selected Profile context

Flight Deck also gained stronger selected-vs-active Profile presentation so users can edit one Profile while another remains active.

### Global notification system

Transient operation feedback moved away from inline page cards and into a global application-level notification system.

The new notification presentation supports:

- top-right floating notifications;
- severity-aware styling;
- timed dismissal;
- hover pause;
- click-to-open details;
- copyable details;
- no page-layout displacement.

### General Flight Deck cleanup

The release also includes safer source labels, stronger modal reuse, cleaner status presentation, more consistent device/Profile context, and additional theme-aware polish across major Flight Deck surfaces.

## Adaptive Response and live telemetry

The live Adaptive Response telemetry path was hardened so real controller telemetry does not depend on the Interactive preview path.

The backend now exposes more complete runtime telemetry and supports bounded presentation history rather than allowing stale UI work to accumulate indefinitely.

Live telemetry work includes:

- per-Rig-member telemetry snapshots;
- bounded history;
- latest-sample coalescing;
- smoother live-controller presentation;
- stronger selected-device targeting;
- propagation of fields such as velocity, acceleration, confidence, prediction horizon, lead, mapped state, and final output where available.

The Interactive preview remains a separate synthetic inspection path.

## Native DirectInput axis identity improvements

v2.6.3 adds deterministic native DirectInput axis metadata for:

- X
- Y
- Z
- Rx
- Ry
- Rz
- Slider 0
- Slider 1

Axis identity is no longer assumed purely from enumeration order. This is especially important for real controllers whose DirectInput descriptors do not arrive in a convenient or predictable sequence.

Focused coverage protects Rz and full-axis/sentinel routing behavior.

## Configuration and migration

The release advances the persisted configuration model to the current v2.6.3 schema while preserving the normal supported upgrade path for existing user data.

The final release also includes a small qualification-fixture correction so release/update validation asserts the actual current persisted schema instead of the stale schema-29 expectation.

## Reliability and regression coverage

v2.6.3 expands focused backend/QML/runtime coverage around:

- exact controller verification;
- reconnect/reacquisition;
- required vs optional Rig members;
- selected-device isolation;
- Profile/category behavior;
- Virtual Output state and vJoy ownership;
- setup convergence;
- Flight Deck presentation contracts;
- live telemetry;
- native axis identity;
- configuration migration and release/update qualification.

## Runtime and architecture

The low-latency DirectInput-to-vJoy mapper remains the governing runtime boundary. Device discovery, setup/readiness inspection, HidHide/vJoy repair, persistence, Profile editing, telemetry presentation, notifications, and other UI/control-plane work remain outside the report-processing hot path.

### Deeper Device Rig ownership migration

One deeper architecture migration is intentionally left for the next architecture campaign: fully replacing remaining concrete Profile/controller/output references with logical Rig-member and output-role references across mapping, Automation, portability, and Signal Flow.

v2.6.3 delivers the user-facing/runtime separation needed for reliable multi-controller operation without forcing that much larger persistence and Signal Flow migration into this release.

The intended long-term architecture remains:

- **Device Rig = hardware topology**
- **Profile = behavior**
- **Activation policy = relationship between them**

## Compatibility and requirements

- Windows 10/11 is the intended runtime family.
- vJoy is required for virtual output when running the mapper.
- HidHide remains optional but recommended when physical controllers must be isolated from a game.
- Controller compatibility remains dependent on each device’s actual DirectInput/HID behavior and the user’s configured setup.
