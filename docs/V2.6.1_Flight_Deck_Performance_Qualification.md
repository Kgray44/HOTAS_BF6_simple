## Findings and disposition

The initial isolated backend sample was a 10-second control-plane run: 91 general telemetry notifications, 213 input-telemetry notifications, zero controller/button model rebuilds, one explicit cached getter read per sampled model, and zero UI event-loop delays over 250 ms. It established a control-plane baseline, not a physical-controller or rendered-frame measurement.

Static review then ranked the avoidable Flight Deck work as follows:

| Rank | Area | Evidence-led bottleneck | Disposition |
| --- | --- | --- | --- |
| A | Axes / persistent profile text | `backend.axes` reconstructed rich configuration and numeric data for every 30 Hz input notification; profile presentation properties also listened to input telemetry. | Split stable axis-card configuration from the small numeric stream; notify profile presentation only after its derived control-plane values change. |
| A | Adaptive Response | QML copied bounded history arrays with `slice(0)`, replay rescanned from the start, and the canvas walked every recorded point on each redraw. | Preserve bounded backend rings; mutate bounded page buffers in place, advance replay with a cursor, and decimate drawing to the visible pixel width. |
| B | Signal Flow | Per-route live telemetry and port membership used repeated linear graph scans; focused wire lookup filtered geometry again. | Build QML presentation-side route, membership, live-telemetry, and wire-geometry indexes at graph/telemetry boundaries. |
| C | Layout and paint | Existing geometry scheduling was already single-shot after graph/layout changes. | Retain it; no renderer rewrite, background timer, visual simplification, or continuous geometry refresh was added. |

The campaign deliberately does not alter `MappingWorker`, DirectInput polling, vJoy writes, adaptive-response math, signal-flow semantics, profile activation, or accepted Flight Deck visual language.

## Implemented control-plane changes

- `AppBackend` now exposes `axisConfiguration` on `stateChanged` and `axisTelemetry` on `inputTelemetryChanged`; the legacy `axes` projection remains unchanged for established surfaces.
- Flight Deck Axes binds card/editor structure to `axisConfiguration` and numeric meter values to `axisTelemetry`. Its card tree is no longer replaced for ordinary input samples.
- Effective-profile presentation values cache their last emitted projection and use `profilePresentationChanged`, preventing physical input samples from waking persistent profile text bindings.
- Flight Deck Adaptive Response retains bounded history in place, uses revisions/counts to repaint safely, samples/repaints at roughly 30 Hz, advances replay incrementally, and keeps the final chart point while decimating dense traces at draw time.
- Flight Deck Signal Flow indexes routes, input/output membership, live telemetry, and wire geometry on their real update boundaries. Existing graph operations and canonical backend commands remain authoritative.
- The QML startup harness has an opt-in `HOTAS_QML_FLIGHT_DECK_PERF_ONLY` isolated navigation probe. It measures all 11 routes without changing normal release-test behavior; its 1500 ms per-route guard is a smoke-stall limit, not a benchmark threshold.

## V2.6.2 Signal Flow integration contract

Any later V2.6.2 Signal Flow integration must preserve the `axisConfiguration`/`axisTelemetry` split, `profilePresentationChanged` control-plane boundary, bounded Adaptive Response replay/drawing behavior, and Signal Flow presentation indexes. It must not move any of this work into `MappingWorker`, DirectInput polling, vJoy output, adaptive math, or canonical graph semantics. Rebase/integration requires a fresh Release all-target build, complete CTest run, and a repeat of the isolated page-navigation probe; conflicts with the separate V2.6.2 candidate are resolved as explicit source changes, never by copying generated build output.
