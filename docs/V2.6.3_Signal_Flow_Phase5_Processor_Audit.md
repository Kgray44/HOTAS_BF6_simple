## Exact gap at the Phase 4 boundary

Phase 4 already draws canonical segments and uses the real visible wire for
Flight Deck hit testing. However, `signalFlowInsertProcessor(segmentId, kind)`
only finds the owning route and delegates to `signalFlowToggleProcessor`. The
processor path is then reconstructed in a fixed source-transform order during
reconciliation. As a result, the selected segment cannot yet determine where
the processor exists in a chain. That is a canonical-model gap, not a QML
problem.

The runtime already has a single canonical order: one-sided domain, deadzone,
center hold, invert, curve, output limits, then Adaptive Response (with an
explicit mixer downstream). Phase 5 therefore treats each persisted segment
ordinal as the transform's real execution-stage target. It rejects a drop on
the wrong stage, exposes only compatible additions for the selected segment,
and never invents a graph-only reorder. This preserves segment and processor
ID lifecycles without introducing graph-local route, processor, configuration,
or segment state.

## Phase 5 implementation result

- `signalFlowInsertProcessor` now resolves the selected durable segment and
  verifies that its ordinal is the requested transform's compiled stage before
  creating one revision-checked undoable source-setting edit.
- `signalFlowAvailableProcessorsForSegment` supplies the true eligible palette
  entries. Both the four shared-theme views and Flight Deck disable incompatible
  chip actions with an explicit stage-selection label.
- Shared processors grow in place. Their owner settings are propagated to a
  newly joined source before reconciliation, and their identity remains stable
  when a member becomes the owner. Joining conflicting shared objects is
  rejected rather than overwriting one configuration.
- `signalFlowRemoveSharedProcessorChannel` removes exactly the selected source
  and all of its fan-out legs from a shared processor, leaves other members
  unchanged, preserves identity during owner handoff, and records one undoable
  canonical command.

## UI baseline and Phase 5 implications

- `FlightDeckSignalFlow.qml` already uses cached canonical segment geometry,
  spatial hit buckets, nearest-wire distance checks, an existing 5 logical
  pixel target preference, direct processor-port anchors, and Phase 4 motion.
- The shared `SignalFlow.qml` now maps canonical segment IDs onto its cached
  painted Bezier/orthogonal wire geometry. Its pointer/drop surface samples
  that same curve/line path and no route-lane drop target remains.
- Both surfaces must keep keyboard/context-menu insertion, meaningful
  inspector actions, reduced motion, and all theme-specific presentation.
- Existing tests prove durable segment persistence, shared owner propagation,
  split-on-external-divergence, stale revisions, anchor integrity, and HOTPATH
  isolation. Phase 5 adds ordered insertion, chain position, removal/bypass,
  shared-channel lifecycle, and cross-surface targeting coverage.
