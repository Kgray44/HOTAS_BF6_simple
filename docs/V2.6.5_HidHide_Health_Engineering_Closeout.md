## Delivered control-plane seam

`HidHideHealthService` projects typed dimensions, stable `HIDHIDE_` App Health findings, activities, repairability, context generation, per-Device-Rig physical-device state, live check progress, cancellation state, and copyable evidence without replacing `ControllerReadinessService`, Setup Truth, Setup Repair, or `AppHealthService`.

The lightweight Essential check is coalesced and never probes the driver directly. A user-requested Full Check runs off the GUI thread, permits one scan at a time, queues a second Full Check behind the first, publishes deterministic 0–100% progress through package, control-open, four GETs, and evaluation, and supports cancellation. Every nonterminal publication keeps `inProgress=true`; cancellation starts no subsequent read, and a bounded in-flight read may complete safely with partial evidence retained. Opening the read-only control endpoint may retry once after a short worker-thread delay; it publishes delayed/elapsed state while it waits and never blocks the GUI or mapping paths. Results whose full Device Rig/controller/output/executable context is stale are discarded.

`hidhide_read_only_protocol` opens only `\\.\HidHide` with `GENERIC_READ` and uses only the documented `GET_ACTIVE`, `GET_INVERSE`, `GET_WHITELIST`, and `GET_BLACKLIST` IOCTLs. It has bounded overlapped waits and preserves each native failure. A successful direct GET is authoritative for the evaluated context; disagreement with inherited/setup evidence is emitted as an explicit `HIDHIDE_DIRECT_GET_*_CONTRADICTION` Doctor finding, never as an inferred repair. No HidHide SET operation, helper invocation, driver/package installation, service change, or repair transaction was added.

Full Check reads bounded local package evidence separately: client and CLI file versions, the on-disk `HidHide.sys` version, one or more Driver Store candidates, any exactly identified active package, and the pending-file-rename restart marker. It never labels the on-disk file as a runtime-loaded driver and it leaves runtime-loaded version or active-package fields `Unknown` when read-only evidence cannot prove them. A missing or incomplete observation remains `Unknown`; version/package disagreement is `Doctor Recommended`; and only a present pending marker yields `Restart Required`. Each active Device Rig member is evaluated against the authoritative direct blacklist using its current exact HID instances. Optional offline members do not become visible by inference; unresolved identity remains `Unknown`.

The only repair routes presented are existing production authorities: mapper-only allowlisting for a proven mapper-exemption fault, or the existing Controller Readiness transaction after exact identity revalidation. Physical identity, managed virtual-output identity, incomplete inspection, recovery waits, and API/package/driver concerns do not gain a new mutation path.

## Presentation and safety boundaries

Overview, Devices, Diagnostics, and Flight Deck all consume the same `hidhideHealth` snapshot. Devices and Flight Deck show Physical inputs, Virtual output, each active Rig member, health progress, and a cancellation control; Diagnostics shows direct GET results, per-member evidence, package/driver details, repairability, and Copy Sanitized Evidence. Legacy and Standard Diagnostics expose Full Check, Review Repair, and Copy Sanitized Evidence. Health observation remains outside `MappingWorker`, DirectInput report handling, vJoy per-report output, Adaptive Response, and profile-control code.

The Doctor handoff writes only a sanitized local JSON summary (version/build, Device Rig ID, finding IDs, dimension states, counts, and native-error summaries) and Doctor must independently revalidate all context. It does not include local executable paths, HID instance IDs, user profile data, raw driver output, or a repair instruction. The inspected Doctor candidate does not implement a `--hotas-handoff` consumer, so HOTAS BF6 prepares this schema as export evidence and launches Doctor without claiming end-to-end handoff qualification or argument acceptance.
