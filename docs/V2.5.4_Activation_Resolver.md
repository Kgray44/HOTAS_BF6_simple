# V2.5.4 Activation Resolver

V2.5.4 replaces competing automatic profile and Device Rig choices with one
low-frequency control-plane decision:

```text
Detected Game / Application category
  → ordered eligible Profile
  → assigned ready Device Rig
  → enabled available Virtual Output
```

It is deliberately outside the DirectInput → MappingWorker → vJoy report path.
The mapper keeps its existing compiled runtime and performs no new discovery,
allocation, persistence, process enumeration, or UI work per input report.

## Selection policy

For a matched, enabled category, the resolver evaluates profiles in that
category's saved order.

1. A valid manual override is scoped to this runtime session and matched
   game/application category. It ends on resume, target invalidation, process
   restart, or a changed game/application context; it is never serialized.
2. A valid active category/profile/rig/output pair remains stable. A newly
   available higher-ranked profile does not replace it mid-session.
3. The first safe `Preferred` profile is selected.
4. If no Preferred profile is safe, the first safe `Fallback` profile is
   selected.
5. `Manual Only` profiles are never selected automatically.

Each candidate must be enabled, own an enabled Device Rig output, have all
required members connected and identity-safe, target an available virtual
output, pass managed-physical-input isolation preflight, and compile a safe
Device Rig runtime. Optional members may remain absent, ambiguous, or awaiting
verification; their routes are omitted and their reduced capability is shown.
The resolver returns a durable reason, structured candidate list, and
actionable blockers whenever it retains, selects, or refuses a configuration.

Windows foreground authority is sampled on the control plane using the
foreground window's PID and `QueryFullProcessImageNameW`, then debounced for
450 ms. A stable foreground category wins; otherwise the active matching
category wins, then configured category order. Process and inventory changes
are generation-stamped, so stale decisions are discarded and recomputed.

An active healthy required rig receives a bounded 3.5-second reconnect grace
after a required-member disconnect. The grace retains only the existing pair;
it never grants a newly eligible route. On expiry the normal fallback policy
applies.

## User controls

Profiles exposes the assigned Device Rig and its readiness, plus a per-profile
Automatic policy (`Preferred`, `Fallback`, or `Manual Only`). The Category view
shows the computed result, the ordered configuration list, and up/down ordering
controls. Overview and Diagnostics show the same current explanation and offer
`Resume Automatic` when a manual override is active. The resolver card also
lists every profile/rig/output candidate and its eligibility, warnings, and
blockers. When a higher-preference safe route is available, `Switch Now`
executes the same coordinated transaction without creating a manual override.

Looking at a category or profile remains view-only. Direct Profile, Category,
and compatible Device Rig activation are intentional manual operations and
create a session override. A Device Rig can never become configured by itself:
the backend selects a compatible Profile and Output together or refuses. The
Devices surface distinguishes a configured route from a route actually in use
by MappingWorker, and shows each member's expected versus seen identity plus
physical and virtual visibility independently. Profiles
without a Device Rig retain their pre-rig manual selection behavior only while
no Device Rig route is active; they are never automatic candidates and cannot
replace an active routed pair.

## Safety boundaries

Automatic Activation can change only the selected profile, Device Rig, and the
existing managed virtual-output visibility transaction. Its preflight blocks a
known HOTAS-BF6-managed physical input that is visible to games, and warns when
that visibility state is unknown. It never hides, unhides, adopts, or otherwise
changes a physical controller's HidHide state.
Physical game visibility remains an explicit Devices-page action and is shown
independently of the resolver outcome.

Profile Hold/Toggle controls and Profile-targeting Automation are compiled
mapping overlays, not Device Rig transitions. They are accepted only when the
target Profile has the exact same assigned Rig as the base Profile; an
incompatible target is rejected before it can create a report-path contribution.

## Persistence and migration

Schema 25 persists the profile automatic-selection policy only. Candidate-era
manual-override keys are accepted as legacy input and immediately cleared;
they are never written back.
When opening schema 24 or older data, each category's saved default profile (or
its first profile) becomes `Preferred`; its remaining profiles become
`Fallback` in saved order. Previous `restoreLastProfile` metadata remains
readable for compatibility but no longer competes with the resolver. A stale
manual-override reference is discarded safely.

Legacy Device Rig `autoActivate`, `activationPriority`, and `fallbackRigId`
also remain readable and serializable for older configurations, but do not
choose a game-aware route. The Category's ordered Profile policy is the only
automatic authority for a category-bound Profile; the Devices and legacy
Profiles surfaces label the retained fields accordingly rather than presenting
them as competing controls.

### Portable Profile and Pack boundaries

`.hbf6profile` and `.hbf6pack` preserve a Profile's automatic-selection
policy, mappings, and portable output requirements. A Device Rig reference and
HidHide physical-device ownership are deliberately machine-local: import never
matches either one by a friendly name. An imported Profile with a source Rig is
left unassigned and reports **Device Rig assignment required** until the owner
explicitly assigns and verifies a destination-machine Rig. Portable output
serialization strips HidHide device-instance ownership, and import defensively
strips it again, so it cannot be carried to another machine.

## Qualification scope

The candidate includes pure resolver tests for Preferred/Fallback/Manual Only,
manual intent, session override expiry, optional versus required readiness,
foreground/generation facts, isolation refusal, reconnect grace, migration, and
a 25,000-transition deterministic invariant corpus. Existing mapping,
automation, upgrade-fixture, QML startup, and release-contract suites continue
to cover the surrounding product contracts.

Those checks establish source, compiled-runtime, and synthetic/fixture evidence
only. They do not prove a particular physical HOTAS, HidHide configuration,
vJoy installation, or rendered desktop acceptance; those remain owner and
hardware qualification steps.
