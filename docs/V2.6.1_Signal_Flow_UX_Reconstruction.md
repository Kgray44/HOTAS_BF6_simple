# V2.6.1 Signal Flow UX Reconstruction

## Phase 0 — design and architecture freeze

**Status:** ready for owner design review; implementation is intentionally not started

**Branch:** codex/v2.6.1-signal-flow-rebuild-phase0
**Scope:** Flight Deck is the reference experience. This document defines the corrective interaction and control-plane boundary for V2.6.1 without replacing production Signal Flow QML.

> The graph itself is the editor. Devices own their ports. Ports create routes. Visible wires are interactive. Processors live on visible routes. All Device Rig members coexist spatially. Supporting UI stays supporting UI.

## 1. Decision and non-goals

V2.6.0's canonical Signal Flow engine is retained. Its graphical presentation and interaction architecture is not retained as a constraint on V2.6.1.

This Phase 0 commit contains only this design freeze and review mockups. It does not:

- alter production QML, C++, configuration schema, runtime mapping, or release metadata;
- start Phase 1;
- merge to main, tag, or release;
- claim native pointer, physical-device, owner-usability, or release qualification.

The reconstruction is therefore **backend-preserving, presentation-replacing**. A later phase may add narrowly scoped control-plane data and commands where the corrected editor cannot truthfully operate from the existing projection.

## 3. Formal V2.6.0 failure analysis

| Failure | Confirmed current architecture | V2.6.1 corrective invariant |
| --- | --- | --- |
| A. Ports were removed from the graph | FlightDeckSignalFlow presents the input and output cards primarily as summaries while the persistent SOURCE BUS and DESTINATION BUS host the routable port lists. | **Graph endpoints SHALL be manipulated directly on graph objects.** Physical device cards own source ports; virtual-output cards own destination ports. |
| B. Visible wires were not the primary target | Wires are painted by Canvas, but Flight Deck supplies a persistent ROUTE LANES column for click/drop/right-click. Generic Signal Flow instead creates a 180 by 20 midpoint surrogate item per route. Neither is geometric wire hit testing. | **The visible route is the route interaction target.** Hover, selection, context menu, delete, focus, and processor insertion operate on the wire itself. |
| C. Processor ports were representational | The graph projection emits processor nodes and a shared-channel count. Flight Deck renders text and small decorative paired dots, but no actual input/output endpoint mapping or port hit targets. | **Processor cards SHALL expose topology.** Every route leg terminates at real processor ports; shared cards expose paired channel ports and resize with their channels. |
| D. Multi-device editing leaked internal scope | signalFlowGraph projects secondary rig members as scopeEditable false. The inspector exposes Edit this input scope, while signalFlowConnectInternal and processor commands resolve editingDeviceMappingForWrite. | **Device ownership SHALL be inferred from the graph object being manipulated.** The backend may resolve an internal focused scope, but ordinary graph routing cannot require the user to choose it first. |
| E. Toolbar capability dump | The Flight Deck page makes filters, Focus, Live, X-ray, learning, alias, fit, auto-layout, lock, density, wire style, motion, defaults, replace-all, zoom, and profile controls persist together. | **Capability existence does not imply permanent toolbar presence.** Primary workflow context stays visible; secondary capability moves to View, Tools, overflow, inspector, or contextual menus. |
| F. Inspector and destination browser were conflated | The right card switches between CARD BUS and DESTINATION BUS, then combines route detail, card detail, output ports, setup links, and route actions. | **The inspector inspects. The graph routes.** Destination selection belongs on destination-card ports, not in a persistent inspector list. |
| G. Workspace did not dominate | The rendered Flight Deck capture dedicates material width to permanent left and right panels and keeps route lanes below a small card canvas. | **The graph workspace is the dominant surface.** With no inspection requested, the canvas receives 80–90 percent of usable Signal Flow content area. |

The design problem is therefore not a paint or palette problem. It is an interaction-surface ownership problem.

## 4. Protected backend boundary

### 4.1 Protected as-is unless a later semantic defect is demonstrated

The following V2.6.0 behavior is protected through reconstruction:

- SignalFlowState as the centrally persisted canonical topology, rather than a QML-local mapping store.
- Stable route, processor, mixer, shared-processor, profile, and controller identity lifecycle.
- Schema-28 compatibility and deterministic migration/project-to-focused-editor reconciliation.
- Analog collision semantics: Replace, Average, Sum Clamped, and Highest Magnitude remain explicit and durable.
- Analog, digital, and native-POV fan-out semantics.
- Mixer identity and bounded runtime compilation.
- Revision-checked mutation, transaction snapshots, undo, redo, and stale-state rejection.
- Focused-editor synchronization and canonical deep-link identity.
- Separately persisted presentation metadata rather than runtime graph state.
- Bounded live telemetry sampled on the control plane.
- DirectInput-to-vJoy isolation: MappingWorker consumes compiled bounded tables; it does not traverse graph/QML objects, serialize, log, lock, or allocate per report.

The current code supports this conclusion. SignalFlowState contains canonical routes, mixers, shared processors, identity records, workspaces, node layouts, and group state. RuntimeMappingConfiguration contains fixed compiled topology tables. The mapping loop branches to those fixed tables and does not ask QML to evaluate topology.

### 4.2 Not protected as a presentation contract

The following V2.6.0 choices are replaceable:

- permanent SOURCE BUS, DESTINATION BUS, CARD BUS, and ROUTE LANES surfaces;
- Canvas-only visual geometry without geometric wire hit testing;
- local port labels such as axis:0 used without a graph-global endpoint identity;
- source-card and output-card summaries that omit their interactive ports;
- decorative processor channel dots;
- current fixed command bar, inspector sizing, and current auto-layout arrangement;
- visible internal editing-scope selection.

### 4.3 Actual canonical-model defect disposition

No runtime/canonical semantic defect was found in this Phase 0 audit. The missing pieces are **control-plane projection and command boundaries**, not a reason to rewrite topology, migrations, or MappingWorker.

## 6. Required control-plane API additions

These are Phase 1+ proposals, not changes in this Phase 0 commit. They are deliberately additive and do not enter MappingWorker.

### 6.1 Graph projection

Add a versioned graph projection that returns the existing canonical objects plus:

| Addition | Purpose |
| --- | --- |
| endpointId | Opaque globally unique identity for every physical source and virtual destination. It includes canonical profile/owner context internally; QML never assembles it from friendly text. |
| ownerNodeId | The device, output, processor, or mixer that owns the endpoint. |
| portDirection, signal kind, availability, compatibility | Lets the graph render and validate a gesture from actual ports. |
| sourceControllerRecordId | Makes every physical endpoint's owning Device Rig member explicit. |
| processorPortId and channelId | Represents actual processor input/output ports, including each shared channel pair. |
| routeSegmentId | Identifies the currently projected edge between two canonical endpoints or processor ports. It is valid only at the returned topology revision. |
| segment capabilities | Describes compatible processor insertion, delete/bypass behavior, and whether the operation expands a source-wide transform. |
| edge/route relationship | Lets selection, live telemetry, deep links, and accessibility identify the underlying canonical route without QML inventing semantic state. |

The graph projection remains a snapshot. Friendly labels, canvas positions, route flattening, hover state, and spatial-index buckets are presentation data; canonical endpoint/route/processor identity is not.

### 6.2 Endpoint-oriented commands

Add commands equivalent to:

    connectSignalFlowEndpoints(sourceEndpointId, destinationEndpointId, collisionDecision, expectedRevision)
    disconnectSignalFlowRoute(routeId, expectedRevision)
    insertSignalFlowProcessor(segmentId, processorKind, expectedRevision)
    removeOrBypassSignalFlowProcessor(processorId, decision, expectedRevision)

The command layer resolves a physical endpoint to its controller/profile mapping internally. It validates the same revision, collision, topology, and runtime constraints as the current commands. It does not silently switch the user's visible editing scope or activate a different profile.

### 6.3 Multi-device mutation adapter

The graph projection already shows secondary Device Rig member cards, but marks them read-only because existing write commands use editingDeviceMappingForWrite. Replace that public interaction dependency with a source-endpoint resolver:

1. QML supplies the opaque endpoint ID from the clicked/dragged card port.
2. AppBackend validates its profile, Device Rig membership, saved-controller identity, capability, and expected revision.
3. AppBackend resolves the appropriate DeviceProfileMapping internally.
4. The existing reconciliation, transaction, undo/redo, and bounded compile path execute unchanged.
5. The graph refreshes from canonical state.

Focused Axes/Buttons/POV editors may continue to require a chosen device context internally. Graph routing does not expose that requirement.

### 6.4 Processor semantics before implementation

The current processor toggle applies source-owned axis settings. A source may fan out, so adding a source-owned Curve on one visible leg can intentionally affect every route from that source. The rebuilt graph must never disguise that fact.

The new segment capability must therefore tell the user which of these semantic cases applies before commit:

- source-chain insertion: affects the source's visible fan-out chain and highlights all affected legs;
- route-local insertion: affects only the selected canonical route when that processor type supports it;
- mixer insertion: is a multi-input structural operation and cannot be bypassed as though it were a one-in/one-out processor;
- shared-processor insertion: creates/joins explicit paired channels only after the owner and every affected route are validated.

If source-owned settings cannot express a requested route-local transform, a later phase must make the canonical extension explicitly. QML must not simulate it with graph-local state.

## 8. Device-card contract

### 8.1 Physical input cards

A physical card represents exactly one saved controller identity. It has a clear connection/missing state and expandable Axes, Buttons, POV Directions, and Native POV groups. Each visible source port appears on the card's right edge, so a route leaves the owning object.

    T.Flight Hotas One                                  Connected · Verified
    Axes                                                          v
      Roll                                                   [source port]
      Pitch                                                  [source port]
      Throttle                                               [source port]
    Buttons                                                       >
    POVs                                                          >

Rules:

- Detailed mode shows named rows and direct ports. Compact mode shows selected/active ports and counts. Overview mode shows grouped anchors and route density, not fake detailed ports.
- Group collapse is persisted per owner card and workspace. A drag begins from an actual port; it may reveal compatible collapsed destination groups temporarily.
- Hovering a source port shows route count, signal kind, device owner, and compatible destination glow.
- Selected source state is local to a graph gesture, visually distinct from inspected-object state.
- Offline and missing cards remain spatially present. Their routes remain inspectable; mutations validate availability according to existing canonical rules.
- A card's global node ID and every port's endpoint ID derive from canonical identity, never from its visible label or position.

### 8.2 Destination cards

Virtual output cards use matching group behavior. Their destination ports appear on the card's left edge. A destination is selected by pointing at its actual port, not by opening a right-hand browser.

### 8.3 Processor and mixer cards

A normal processor has a left input port and right output port on its visible route. A shared processor has one labeled input/output pair for every channel. A mixer exposes each incoming port, an explicit output, and its mode. Dynamic height is data-driven by active channels; rows do not collapse into decorative dots.

## 9. Selected wire-interaction architecture

### Decision

Use **Canvas for bounded visual rendering plus a single geometry-aware interaction layer backed by a cached spatial index**. Do not use per-route midpoint rectangles, permanent route lanes, or a list surrogate.

This reuses V2.6.0's useful boundary: geometry is rebuilt after canonical topology, card placement, viewport, or semantic-zoom changes, not from report-rate telemetry. Live state repaints color/weight only.

### 9.1 Scene geometry

For each graph projection revision, the view builds a presentation-only GraphSceneGeometry cache:

1. Resolve card bounds and actual port-anchor coordinates from the rendered card delegates.
2. Expand each canonical route into ordered visible segments: source to processor input, processor output to next processor input, and final output to destination.
3. Assign every segment its projection-supplied routeSegmentId, style, bundle key, route z/order, and bounding box.
4. Flatten smooth curves to a small bounded polyline for distance tests; preserve orthogonal segments directly.
5. Place segment bounding boxes, expanded by hit radius, in fixed logical-space grid buckets. Rebuild only when geometry changes.
6. Paint the same cached geometry in Canvas, including bundle trunks, crossings, selected state, X-ray, and reduced-motion rules.

The cache may live in QML for the first bounded Flight Deck implementation if profiling supports it; a small C++ scene-projection helper is preferred if fixture density shows frame-time instability. In either form it is a derived interaction cache, never a mapping model and never hot-path code.

### 9.2 Pointer behavior

- The interaction layer owns hover, click, right-click, drag-over, and keyboard-focus correlation for the visible line geometry.
- Hit width is at least 20 logical pixels centered on a thin visible wire; touch/pen may use 28 logical pixels. Endpoint ports take precedence in their own magnetic area.
- Candidate selection uses point-to-polyline distance, then distance to the relevant visible segment, then selected-route affinity. At a crossing, the closest segment wins; a small disambiguation popover appears only when candidates remain visually indistinguishable.
- Hover state is stable across adjacent segments of the same route. A selected route receives higher visual and candidate priority until the pointer clearly exits its hit envelope.
- Right-click opens the contextual route menu at the actual segment. Delete disconnects the selected route after the existing revision check.
- During processor drag, compatible visible segments highlight. Target hysteresis retains the current compatible candidate until another candidate is materially closer or the pointer leaves an expanded envelope; it never jumps merely because two paths cross.
- Accessible route navigation is a semantic tree/command model keyed to the same route/segment IDs. It is not a visible route-list substitute.

### 9.3 Dense graph performance

The cost model is explicit:

- topology/layout change: bounded geometry and bucket rebuild;
- pointer move: query only overlapping grid buckets, then test a small candidate set;
- live telemetry: Canvas repaint from cached paths only;
- route selection: no re-layout;
- no DirectInput, MappingWorker, vJoy, configuration serialization, or logging work is added to report processing.

Orthogonal and smooth styles share the same segment identity. Bundles remain visually compact but expand enough under hover for a user to select individual legs.

## 10. Processor interaction contract

### 10.1 Direct insertion workflow

1. Select Add Processor from a selected wire's context menu, drag a processor from the contextual palette, or invoke the keyboard equivalent.
2. Move over the graph; only compatible actual wire segments receive a highlight.
3. The nearest compatible segment locks with the hysteresis rules in section 9.
4. Show a split preview: route before segment, processor card with real ports, and route after segment.
5. Drop commits one revision-checked canonical command.
6. Animate the split from the old wire into the two new visual legs. Reduced Motion shows the same structural change without travel animation.

### 10.2 Removal and sharing

- A one-in/one-out processor may be bypassed only after validation; its visible legs join and the owner receives an explicit confirmation if other fan-out routes are affected.
- A mixer may not be silently bypassed. If removal would leave multiple analog contributors, the user chooses a visible replacement/disconnect outcome.
- Shared processors show paired channel rows. Adding a channel grows the card; splitting a channel visibly produces a distinct local processor card and route legs.
- Curve and Adaptive Response cards retain canonical deep links. Returning lands on the exact selected route/processor context rather than merely the page.

## 11. Multi-device contract

All active Device Rig members coexist on the same graph. A user can begin a route on any physical card; the source endpoint carries its owner identity.

    [Joystick] Roll o -----------+----------------------------> o X [vJoy]
                                  |
    [Throttle] Throttle o -------+----------------------------> o Slider
                                  |
    [Pedals] Yaw o ---- [Curve] o+----------------------------> o Rz

The user does not choose an Edit this input scope step to route Throttle, Pedals, or Button Box. Graph commands resolve the corresponding device mapping internally. The existing focused editor remains a focused-editor concern, not a prerequisite for graph manipulation.

## 15. Corrected test strategy

V2.6.0 tests proved substantial semantic work: migration, topology, canonical commands, runtime compilation, QML execution, visual stress construction, and bounded behavior. They did not prove that a person can discover or manipulate graph topology spatially. A source-string contract or an offscreen QML snapshot is not usability evidence.

| Layer | Required proof |
| --- | --- |
| Semantic tests | Canonical topology, stable IDs, schema-28 migration, collisions/mixers, fan-out, sharing, undo/redo, focused-editor synchronization, and bounded runtime compilation. |
| Control-plane projection tests | Globally unique endpoints, all-rig-member graph projection, segment/processor-channel identity, stale-revision rejection, and no accidental profile activation. |
| Interaction tests | Actual PointerHandler/MouseArea coordinate gestures on card ports and cached visible-wire geometry: hover, click, right-click, drag, crossing disambiguation, processor insertion, delete, keyboard equivalent, and small-window behavior. |
| Native visual tests | Real rendered Windows application captures at required DPI/window bands, with actual resolved fonts and no offscreen substitution claim. |
| Performance tests | Geometry rebuild and hit-testing at dense fixtures on the UI/control plane; existing MappingWorker hot-path benchmark remains separately frozen. |
| Owner acceptance | The 17 native tasks above, completed by a human with ratings and any exception disposition. |
