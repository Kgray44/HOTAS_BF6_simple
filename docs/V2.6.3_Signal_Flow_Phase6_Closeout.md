## Canonical fan-in representation

Phase 5 routes and route-qualified processor segments remain canonical. Its
old mixer record named only a destination and inferred contributing routes, so
it could not express durable multi-input topology without side state. Phase 6
adds the minimal central representation:

- `SignalFlowMixer::inputs`: a bounded, ordered list of
  `SignalFlowMixerInput` records, each naming one exact canonical route identity
  and one durable mixer-input port ID;
- `SignalFlowMixer::outputPortId`: the one durable mixer output port;
- validation that deduplicates inputs, rejects unrelated/inactive routes,
  removes invalid one-input mixers, and disables unnamed analog collisions;
- JSON and portable-profile remapping for the new identities.

The graph projects one source-to-input edge per named input and exactly one
output-to-destination edge, carried by the first durable input. QML receives
that projection; it does not manufacture input lists, mixer ports, or output
wires. A source may fan out normally, but multiple analog sources may share a
destination only when every enabled contributor is named by its active mixer.

## Mixer execution and lifecycle

The shipping modes are deliberately limited to behavior already representable
in the fixed compiled runtime table:

- **Average**: arithmetic mean of available named inputs.
- **Sum Clamped**: summed available named inputs, clamped to `[-1, 1]`.
- **Highest Magnitude**: input furthest from neutral; exact ties retain the
  earliest durable mixer-input order.

Compiler order now follows the durable input sequence, so the tie rule is not
an accidental physical-axis enumeration side effect. Compilation happens only
at configuration boundaries; the report loop continues over fixed bounded
route tables with no graph traversal, string lookup, allocation, or logging.

The collision interaction rejects a second direct analog connection until the
operator chooses Replace or one of the vetted mixer modes. Mixer create,
growth, mode changes, input removal, and mixer removal are revision-checked
snapshot commands with one persistence/compile boundary and one Undo entry.
Removing an input disconnects that source. If one remains, the mixer is
removed only through the deterministic simplification path; removing a mixer
disconnects all of its named inputs and never silently selects a survivor.

Buttons retain their established canonical multi-source OR endpoint behavior.
It is already a real compiled output behavior, so Phase 6 adds no decorative
button-combiner processor.

## Default Connections

The backend generates a deterministic, non-mutating plan from a unique
canonical alias match or a stable axis pairing. It exposes row-level
**Added**, **Kept**, **Replaced**, **Mixer changes**, **Ambiguous**, and
**Blocked** categories in Standard and Flight Deck. Connect Unassigned Only
preserves every existing source route and marks analog destination collisions
for a deliberate decision. Replace All constructs the entire target topology
before mutation, reports every replaced route and removed mixer, and refuses
to apply while a block or ambiguity remains.

Applying rechecks the preview revision, validates the current plan, replaces
the scoped routes in one transaction, persists/compiles once, and records one
undo command. An older preview therefore fails without overwriting a newer
editor change. Saved offline device scopes remain valid: their plan rows say
`OFFLINE / configuration valid, live signal unavailable`, rather than being
silently omitted or reported as Ready.
