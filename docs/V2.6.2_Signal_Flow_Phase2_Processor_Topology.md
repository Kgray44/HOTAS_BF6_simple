# HOTAS BF6 Simple V2.6.2 — Signal Flow Phase 2 processor topology

**Candidate status:** implementation and native qualification candidate only.
This record does not authorize a merge, tag, release, schema/version promotion,
physical-device claim, or owner acceptance.

## Intent and fixed boundaries

Phase 2 starts from the accepted V2.6.2 Phase 1 baseline and reconstructs
processor placement as canonical control-plane topology. It preserves the
existing runtime compiler and MappingWorker report path: DirectInput sampling,
compiled mapping, vJoy output, hot-path allocation behavior, and performance
budgets are unchanged.

The five supported visual themes remain compatible with the same `signalFlowGraph`
projection. Flight Deck is the reference interaction surface; generic themes
retain their established presentation contracts.

## Canonical model

Each `SignalFlowRoute` now owns a durable ordered `segments` collection. A
segment has its own stable ID and explicit source/destination endpoint IDs.
The chain begins at the physical source endpoint, visits a distinct input and
output endpoint for every real processor identity, and ends at the virtual
destination endpoint. `processorPath` is retained only as the existing
compatibility projection consumed by focused editor/runtime compilation.

Processor ports use route-qualified endpoint IDs:

```
sf-endpoint:<route-id>:source
  -> sf-port:<processor-id>:<route-id>:in
  -> sf-port:<processor-id>:<route-id>:out
  -> sf-endpoint:<route-id>:destination
```

Consequently, a shared processor receives one truthful input/output port pair
per participating route. It does not collapse into a decorative shared dot or
pretend that multiple channels are one wire.

Segments persist with the schema-28 Signal Flow payload. Older payloads with
no segment collection remain loadable; reconciliation deterministically
backfills the additive topology. Imported routes discard their former segment
identities together with their route identities, preventing stale cross-profile
selection or endpoint reuse.

## Commands and safety

`signalFlowInsertProcessor(segmentId, kind, expectedRevision)` resolves the
clicked/dragged canonical segment before delegating to the existing atomic
processor transaction. It therefore retains existing persistence, undo/redo,
focused-editor synchronization, and runtime compilation behavior while no
longer accepting a graph-local route-lane target.

`signalFlowRemoveOrBypassProcessor(processorId, expectedRevision)` provides
the corresponding safe path. It refuses stale revisions, missing identities,
shared processors, and mixers. A mixer is never silently bypassed because that
could imply an unreviewed analog merge; a shared processor requires an explicit
split/shared resolution. Ordinary single-route processors use the existing
transaction and yield an explicit reconnecting segment chain.

The present mapper evaluator has a fixed, source-native semantic processor
order. Segment selection determines the real canonical route being acted on;
it does not claim a new arbitrary runtime execution ordering. This deliberately
avoids a report-path behavior change in Phase 2.

## Flight Deck interaction

The Flight Deck wire cache reads `route.segments` directly. Each visible wire
starts/ends on a physical input, virtual-output, or processor IN/OUT port.
The spatial hit buckets retain the canonical segment ID, so click, hover,
right-click, keyboard/inspector actions, and processor drag/drop all target
the same edge Canvas painted.

Processor-drag hover uses sticky selection bias only for the currently
previewed segment. A materially closer segment wins the hit test, preventing
target oscillation around crossings. The candidate preview highlights the
actual wire and marks `INSERT`; no route lane, invisible drop strip, bus, or
graph-local surrogate participates. Structural commits reuse the existing
reveal/retire animation path and respect reduced motion.

Processor cards render actual channel-labelled IN/OUT ports, include 30 px
pointer targets and accessible descriptions, and expose existing Curve and
Adaptive Response full-settings deep links. The inspector offers the safe
remove action and preserves selected segment context across editor return.

## Owner review addendum — live node drag / wire attachment

Owner review found that a moved card could leave wires at an earlier location.
The direct cause was in the presentation cache: input and output `GraphPortRow`
delegates recorded their graph-space centers only when the row itself changed.
Dragging a card changes its parent `x`/`y`, not the child's local row geometry.
`noteNodePosition()` then restarted the general wire timer, while
`rebuildWireGeometry()` read the stale absolute `portAnchors` map. The result
was a visually moved card paired with a prior port center. Processor markers
did report parent-derived `sceneX`/`sceneY`, but still went through the same
deferred whole-cache refresh rather than an affected-segment path.

The correction is presentation-plane only and has two explicitly separate
lifecycles:

- During drag, `liveNodePositions` holds an unpersisted graph-space card
  position. Each real delegate anchor is remembered both in graph space and as
  a card-local offset. Resolving an endpoint therefore uses the current live
  card position plus that offset, preserving `visible port center == wire
  endpoint` without a child-local move notification.
- Each cached segment records its source/destination node and endpoint IDs.
  `refreshLiveDragGeometry()` replaces only segments incident to the moved
  node, updates only their spatial hit buckets, and requests Canvas paint.
  It uses the allowed drag-simplified route while direct manipulation is
  active; complete obstacle routing runs once on release.
- Release moves the final transient position into the presentation position
  map and calls `signalFlowSaveNodeLayout()` once. The resulting graph refresh
  supplies the one complete route rebuild. There is no workspace save,
  serialization, backend routing command, or MappingWorker work on a pointer
  update.

Live updates execute synchronously for each delivered pointer change and ask
Canvas for the next render; there is no polling, easing, spring, or catch-up
animation. Card position behaviors are disabled only for the dragged card.
Normal non-drag anchor/layout changes are coalesced to the next event turn.

The QML lifecycle test now drives a deterministic fixture containing Input A
Roll/Pitch/Yaw, Input B Roll, BF6 output X/Y/Z/Rx, and the chain
Input A Roll → Curve → Adaptive → Output X. It samples thirty intermediate
positions for every moved card and asserts endpoint-to-current-anchor distance
within 0.01 graph pixels, affected-only updates, no full rebuild during drag,
and one release rebuild. It also exercises 1-, 8-, and 28-route dense inputs:
each 30-sample drag produces 30 live geometry updates and respectively
30/240/840 affected-segment updates with zero persistence writes in the
synthetic fixture. The native-backed QML surface additionally proves zero
placement writes during movement and exactly one successful placement write
plus one release rebuild.

The fixture moves at 100%, zoomed-in, and zoomed-out scales with a panned
viewport. It updates an anchor after a simulated group/density geometry shift,
then rechecks the same endpoint invariant. `GraphPortRow` also observes
height changes now, so real group expansion/collapse and density-driven row
resizing re-register the graph-space center without a polling path.

## Owner review addendum #2 — port-anchor integrity audit (pre-change)

This audit distinguishes the accepted live-drag latency correction from the
new endpoint-integrity defect.  The old drag path did update incident segments
promptly; it did not, by itself, guarantee that the endpoint it supplied was
the currently rendered port center.

### Coordinate contract

The one coordinate system used by route geometry is the unscaled logical
coordinate system of the `scene` `Item`.

| Value | Coordinate space | Producer / consumer |
| --- | --- | --- |
| `GraphPortRow.x/y`, processor marker `x/y` | local to the port row or processor card | Qt Quick layouts / marker delegate |
| card `x/y` and `nodePositions`, `liveNodePositions` | `scene` logical graph space | card bindings, persisted layout, transient drag state |
| measured `portAnchors` | `scene` logical graph space | `mapToItem(scene, ...)` from the actual visible port |
| `portAnchorOffsets` | card-local graph offset (`port center - current card position`) | derived only from a `scene` measurement and current card position |
| `wireGeometry`, Canvas paths, buckets and wire hit testing | `scene` logical graph space | geometry builder, Canvas and `hitWire()` |
| `zoom` | a visual scale on `scene` | applied outside the logical geometry |
| Flickable `contentX/contentY` | viewport clipping / scroll translation | applied outside `scene`, never stored in an anchor |

Consequently zoom and pan must be applied neither to a measured anchor nor to
a wire endpoint.  A card's persisted and transient positions use the same
logical graph convention.  Object identity may be supplied as `objectId` or
`id`; lookup must accept both, but the local placement map is keyed by the
durable storage identity when present.

### Findings before the correction

1. Device input/output rows measured the center of their 30 px hit target with
   `mapToItem(scene, ...)`; that point is intentionally also the 10 px dot
   center.  Processor markers instead reconstructed a point by adding card and
   marker coordinates.  The two paths happened to be equivalent today but
   were competing coordinate formulas.
2. `GraphPortRow` scheduled `Qt.callLater(updateAnchor)` from its local
   `x/y/width/height` notifications.  A group/header or ancestor card relayout
   can move a row without changing those local values, leaving the remembered
   offset from its former row position.  It also left a deferred JavaScript
   callback across Repeater delegate destruction/recreation.
3. `onGraphChanged` cleared all anchor state and immediately rebuilt wire
   geometry.  Delegate creation and its deferred registration happened later,
   so that rebuild could consume fallback or stale measurements.  This is a
   registration-order defect, not a zoom or pan transform defect.
4. Release did promote the final live position before clearing the transient
   map, avoiding the obvious old-position gap, but the synchronous backend
   graph refresh then cleared the measurements before replacement delegates
   had reported their new centers.  It therefore still admitted a stale or
   fallback stable result after a relayout.
5. The insertion-preview path read `portAnchors` directly, while normal and
   live geometry resolved `portAnchorOffsets`; this was a third competing
   access path.  Canvas hit testing uses cached segment endpoints and must
   therefore be rebuilt from the same conceptual center as drawing.

The correction below must use one `currentGraphSpacePortCenter()` resolver,
refresh all visible port measurements through a geometry-driven event turn,
and retain the incident-segment drag optimization.  It must not introduce a
delay heuristic or a full graph rebuild on each pointer event.

### New Phase 2 exit gates

    stable graph states.
34. Live-drag endpoint coordinates and post-release stable coordinates converge

35. No route can remain attached to an old or stale card position after drag.
36. Group, density, zoom, pan, and layout changes preserve endpoint correctness.

## Owner review addendum #2 — corrected candidate record

### Implemented port-center and selection invariants

`currentGraphSpacePortCenter()` is now the sole endpoint resolver.  It first
combines the current logical card position (including an active live-drag
position) with a measured card-local port offset, then uses a fresh direct
scene measurement only while a delegate is being created, and finally uses a
bounded card-geometry fallback only before a rendered port exists.  Canvas
geometry, segment hit buckets, live-drag replacement geometry, and the
processor insertion preview all call this resolver.  Device rows and
processor markers both obtain their measurement from the actual visual center
via `mapToItem(scene, ...)`.

Anchor remeasurement is event-driven.  Each port owns a zero-interval Timer
that is cancelled with its delegate; a graph/layout epoch asks currently live
delegates to measure again.  Graph replacement clears the old measurements,
requests that epoch, and coalesces one stable rebuild after registration.  A
repeated measurement that has not moved does not clone anchor state or request
another Canvas frame.  The live pointer path still updates only incident
segments and does not perform an anchor pass per pointer frame.

Clicking empty graph space now calls `clearGraphSelection()`.  It clears the
route, canonical `selectedSegmentId`, node, and source selection together.
This matters because Canvas renders its selected trace from the segment ID;
clearing only the route object had left a visible selected trace after an
outside click.

### Isolated-review and exit investigation

The focused `--isolated-presentation-signal-flow` launch is now included in
the backend's smoke-safe boundary.  It uses test-mode settings and the normal
interactive event loop, but does not start the DirectInput/mapping worker or
acquire vJoy/foreground-game state.  It has no auto-close timer.  The separate
`--signal-flow-idle-probe` is explicitly diagnostic-only and exits after four
seconds; it reported 16 Canvas paints, 3 geometry rebuilds, and one anchor
epoch in the rebuilt package.

The earlier owner candidate exited on 2026-09-11 at 16:10:48 local.  Its local
crash report is `Crash Reports/2026-09-11_16-10-47_23992_0`: Windows 11 25H2,
HOTAS BF6 2.6.2 build `47ab27ea5b99`, `0xC0000005` access violation, fault
module `Qt6Qml.dll`, and a successfully written minidump.  The report's
recent-events log contains no useful breadcrumb, and the Windows Application
and System logs contained no matching WER/Application Error record.  No local

## Post-addendum requalification — geometry handoff and fixture isolation

The follow-up correction keeps an existing route visible while a release-time
obstacle reflow is resolved.  At release it snapshots the incident wire
geometry, calculates the stable geometry from current port centers, then
interpolates corresponding curves over a short cubic transition.  This is a
geometry morph, not a fade-out/fade-in or a second route rendering pass.  The
source and eligible destination ports also expose their connection state more
prominently, and the temporary drag wire's endpoint is derived directly from
the pointer position rather than a midpoint calculation.

The endpoint defect had a second ordering facet: a graph replacement cleared
anchors and requested delegate measurements, but a coalesced wire rebuild
could occur before a group or density row had completed its final layout.
`onGraphChanged` now defers the geometry handoff until currently live port
delegates have queued their zero-turn measurements; direct stable
`nodePositions` replacement also schedules a final cache rebuild.  Thus the
old geometry remains available for the morph, while the target geometry is
resolved only from current card-local port offsets.  No zoom or viewport-pan
value enters either representation.

The owner-fixture `Fit` operation also exposed a test-only source of false
failures: the ordinary 650-ms workspace-save debounce could reload the real
backend graph while the native test temporarily owned a synthetic graph.  The
timer is now named and stopped only by that synthetic fixture after its own
`Fit` call; normal product workspace persistence is unchanged.

Fresh local requalification on this branch completed as follows:

- The focused 3,072-operation rendered-port campaign completed with 47,200
  samples, zero endpoint-integrity failures, and `max_error=0.000000`.
